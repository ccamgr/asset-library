# 実装開始前の決定事項

デスクトップアプリの実装に入る前に、変更コストが高いものだけを先に決める。UI の細部や将来ストア対応は、初期版の利用を見ながら後で変更してよい。

## 最初に決めること

| 項目 | なぜ先に必要か | 推奨する初期値 | 保留した場合の影響 |
| --- | --- | --- | --- |
| 対象 OS | インストーラー、ファイルパス、検証環境が変わる | **Windows 10/11 のみ** | macOS/Linux対応を含めると初期開発とテストが増える |
| アプリ構成 | コード構造と開発環境を決める | **Tauri 2 + React + TypeScript + Rust** | 画面実装を始められない |
| ライブラリの所有方式 | バックアップ・削除・移植の根幹 | **コピー管理を既定、外部参照も初期版から提供** | 後から追加するとファイル移行が必要になる |
| アセット保存先 | 容量・クラウド利用時の動作に影響する | **DBと別に設定可能。初期版は任意のローカルフォルダ、将来はS3/WebDAVを追加** | DBと一緒に固定すると大容量運用へ移行しにくい |
| 初期ライブラリ位置 | 初回起動と可搬性に影響する | **OSのアプリローカルデータ領域に固定** | SQLiteの安全な保存先を一貫させ、初回設定を簡潔にする |
| アセットの単位 | DB スキーマと画面導線を決める | **商品／用途上のまとまりが1アセット。複数ファイル可** | ファイル単位で始めると関連ファイルの統合が難しい |
| 削除の意味 | 誤消去を防ぐ | **「ライブラリから外す」と「実ファイルをごみ箱へ」を別操作** | 実装後に安全な移行が難しい |
| 重複判定 | インポート処理に組み込む必要がある | **SHA-256 + 商品URLの正規化で候補提示。自動統合しない** | 大量登録後の重複整理が大変になる |
| ネットワークの扱い | プライバシーとオフライン性を守る | **既定オフライン。BOOTH情報取得は明示操作時のみ** | 後から仕様変更すると利用者の信頼に影響する |

## ライブラリフォルダの仕様（推奨）

「アプリのインストール先」と「ユーザーデータを保管するライブラリフォルダ」は分ける。Windows のインストール先（通常は `Program Files`）にユーザーのアセットを置かない。

| 場所 | 既定 | 内容 | バックアップ対象 |
| --- | --- | --- | --- |
| アプリ本体 | インストーラーが選ぶ場所 | 実行ファイル、アプリ更新用のファイル | いいえ。再インストール可能 |
| ライブラリフォルダ | OSのアプリローカルデータ領域 | `library.db`、サムネイルキャッシュ | いいえ。アセット保存先のDBバックアップから復旧できる |
| アプリ設定 | OSのアプリ設定領域 | 最後に開いたライブラリフォルダなど、端末固有の軽い設定 | 原則不要。別PCではライブラリを選び直せる |

初回起動時に、ユーザーはアセット保存先とDBバックアップ先を指定する。ライブDBの保存先は選択させない。

1. **アセット保存先を変更する** — アプリが実体を新しい保存先へコピーして検証後に切り替える。元ファイルは自動削除しない。
2. **DBを復元する** — アセット保存先の `database-backups/` から、アプリローカルのライブDBを復元する。
3. **外部ファイルを参照する** — アセットごとに、保存先外の Downloads 等をコピーせず参照する。このファイルはアプリのバックアップ対象に含まれないことを明示する。

このため、アセット保存先とその `database-backups/` を保全すれば復元できる。新しいPCではアプリをインストールし、アセット保存先を選択してDBスナップショットを復元する。

## 早めに方向を決めたいこと

| 項目 | 選択肢 | 推奨 | 理由 |
| --- | --- | --- | --- |
| UI ライブラリ | shadcn/ui系、MUI、独自 | React の軽量コンポーネント基盤 + 独自テーマ | カード一覧とタグ編集を作りやすく、見た目をVRアセット管理向けに調整しやすい |
| 検索 | SQLite `LIKE`、SQLite FTS5 | **FTS5 を初期から採用** | 名前・作者・メモ・タグの横断検索を後から高速化しやすい |
| DBアクセス | Tauri SQL プラグインをUIから使用、Rust リポジトリ層で使用 | **Rust リポジトリ層に閉じる** | ファイル操作とDB更新を一つのユースケースにまとめ、画面から生SQLを出さない |
| ID | SQLite連番、UUIDv7/ULID | **UUIDv7 または ULID** | ライブラリフォルダをコピー・将来統合するときに衝突しにくい |
| サムネイル | 元画像を直接表示、アプリ内コピー+縮小版 | **原本コピー + 縮小キャッシュ** | URL失効・元ファイル削除後にも表示でき、一覧が速い |
| バックアップ | 手動コピーだけ、自動スナップショットも作る | **まず手動コピーを正規手段、DB自動バックアップは後続** | 初期実装を単純に保ち、復元手順を明快にする |

## 後回しでよいこと

- 正式なアプリ名、ロゴ、アイコン、配色。
- BOOTH/Gumroad の細かな項目対応とページ解析の精度。
- ブラウザ拡張、Native Messaging Host、Firefox 対応。
- 圧縮ファイルの展開・中身解析・UnityPackage 解析。
- macOS/Linux、端末間同期、自動アップデート、コード署名。
- カテゴリを一件だけにするか複数にするか（DB は多対多にしておく）。

## 推奨する v0.1 のスコープ

ネットワーク不要のローカル機能だけを先に完成させる。

1. ライブラリフォルダを初回に指定する。
2. ファイル／フォルダをドロップして、コピー管理または外部参照で登録する。
3. タイトル、作者、商品URL、ショップURL、タグ、カテゴリ、メモ、カバー画像を編集する。
4. 一アセットへ複数ファイルを追加する。
5. キーワード・タグ・カテゴリで検索し、ファイル／URLを開く。
6. アセット間の関連（追加、必須、対応、派生、関連）を作る。
7. ライブラリフォルダを丸ごと別の場所へコピーして開けることを検証する。

ここまでを終えてから、BOOTH URL からの情報取得、次にブラウザ拡張による自動登録へ進む。これなら外部サイトの仕様変更や拡張のインストールに影響されず、ライブラリ自体の価値を先に検証できる。

## 最初の実装スパイクで確認すること

本実装前に、使い捨ての小さな検証で次を確認する。

1. Tauri のファイル選択・DnD から Rust 側へ安全にパスを渡せる。
2. 指定した任意のライブラリフォルダに SQLite DB とサムネイルを作れる。
3. 大きな ZIP のハッシュ計算をバックグラウンドで動かしても UI が固まらない。
4. 1,000件程度のダミー資産を仮想化リスト／グリッドで滑らかに表示できる。
5. ライブラリ配下の相対パスが、フォルダをコピーした後にも解決できる。

このスパイクが通れば、フレームワーク選定を事実上確定して v0.1 の実装へ進める。
