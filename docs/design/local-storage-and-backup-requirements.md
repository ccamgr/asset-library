# ローカル保存・容量管理・バックアップ要件

## 1. 決定

SQLite DB とサムネイルキャッシュは、ユーザーのローカルディスクにだけ置く。pCloud を含むクラウドマウント／ネットワークドライブを DB の保存先には使わない。

管理対象アセットの実体は DB／キャッシュとは別の「アセット保存先」に置く。既定ではライブラリフォルダ内とするが、別ローカルドライブや、pCloud Drive などでマウントされたドライブを指定できる。アセット実体は SQLite のようなファイルロックを必要としないため、接続断・低速時の扱いを明示すればクラウドマウント先を利用できる。

クラウドストレージは、アプリがローカルで完成させたバックアップをコピーする**バックアップ先**としても使う。これにより SQLite のロック・同期方式と仮想ドライブの相性問題を避ける。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| アプリ本体 | 実行ファイル。通常は `Program Files` 等にインストールされ、ユーザーデータは置かない。 |
| ライブラリフォルダ | アプリが日常的に利用するローカルデータのルート。ライブDB、サムネイルキャッシュ、書き出しデータを含む。消えてもアセット保存先から復旧できるデータだけを置く。 |
| アセット保存先 | アプリ管理で取り込むアセット実体、サムネイル正本、DB復旧用スナップショットのルート。初期版ではローカルフォルダから選べる。将来はpCloud等のマウントドライブ、S3、WebDAVをストレージバックエンドとして追加する。 |
| バックアップ先 | ライブラリの安全なコピーを置く任意のフォルダ。pCloud Sync フォルダまたは pCloud Drive のマウント先を選べる。 |
| スナップショット | ある時点で復元可能な DB、マニフェスト、必要なアセットコピーの組。 |

## 3. ライブラリフォルダ

### 3.1 場所

- ライブラリフォルダは OS のアプリローカルデータ領域（Windowsでは `%LOCALAPPDATA%/VRAssetLibrary` 相当）に固定する。
- DBとキャッシュは比較的小さく、ロックの正確性が必要なため、利用者が保存先を選ぶ対象から外す。
- 容量の大きいアセットとDBバックアップは、初回セットアップ／設定画面で別々に指定する。

### 3.2 レイアウト

```text
VRAssetLibrary/                         # ライブラリフォルダ（ローカル）
├── library.db                           # ライブ SQLite DB
├── thumbnail-cache/                     # 再生成可能な縮小画像キャッシュ
└── exports/                             # ユーザーが明示的に作った書き出し

<asset-storage-root>/                    # アセット保存先（初期版は任意のローカルフォルダ）
├── assets/
│   └── <asset-id>/
│       ├── cover.<original-extension>   # 商品サムネイルの正本
│       └── files/
│           └── <asset-file-id>-name.zip
└── database-backups/                    # 復旧用の整合性済み SQLite スナップショット
    ├── <timestamp>.db
    └── latest.json

%TEMP%/VRAssetLibrary/                    # OS Temp配下のアプリ専用一時領域
└── <import-id>/                          # コピー・登録中のみ存在する
```

- アセットを「コピー管理」で登録した場合、実体はアセット保存先の `assets/` 配下へコピーする。
- DB内の `asset_files.relative_path` は、ライブラリフォルダではなくアセット保存先からの相対パスとする。アセット保存先を移動した場合は、設定上の保存先ルートだけを切り替えればよい。
- BOOTH等から得た商品サムネイルまたはユーザー指定画像の正本は、対象アセット内の `assets/<asset-id>/cover.<extension>` に置く。ライブDBが消えても、アセット保存先にある正本から再構築できる。
- 一覧で使う縮小版はローカルの `thumbnail-cache/` に置く。キャッシュを消しても各アセットの `cover.*` から再生成でき、アセット保存先がオフラインでも既に生成済みの一覧は閲覧できる。
- `database-backups/` には、アプリが作成した整合性済みのDBスナップショットを置く。ローカルのライブDBが消えた場合、この保存先を選択して復旧できる。
- pCloud等のマウントドライブをアセット保存先にした場合、ファイルを開く／コピーする操作が接続状態や回線速度に左右される。接続断時はアセットを「一時的に利用不可」と表示し、DBを壊れた状態として扱わない。
- 外部参照モードは提供するが、参照先はライブラリとバックアップの対象外であることを常に表示する。
- ライブDBとサムネイルキャッシュはアセット保存先へ置かない。特に pCloud等の仮想マウント先に `library.db` を置くことは許可しない。

## 4. 容量管理

### 4.1 必須機能

- 設定画面に、ライブラリ、管理アセット、サムネイル正本、サムネイルキャッシュ、DB復旧用バックアップ、Temp、外部参照の容量と件数を表示する。
- インポート前に、対象ファイルサイズと必要な空き容量を確認する。容量不足ならコピーを開始せず、保存先変更または空き容量確保を案内する。
- インポート中の一時ファイルには OS Temp 配下の `VRAssetLibrary/<import-id>/` を使い、コピー完了後にアセット保存先へ確定する。途中失敗した一時ファイルは次回起動時に安全に掃除できる。
- サムネイルキャッシュを削除・再生成できる。キャッシュ削除でアセット実体や登録情報を失わない。
- 初期版はファイルハッシュを計算せず、同一ファイルの重複検出・統合は行わない。将来、明示的またはバックグラウンドのハッシュ計算を有効にした場合だけ重複候補を提示する。

### 4.2 後続機能

- ファイル実体をハッシュ単位で一つだけ保存する内容アドレス型ストレージ（重複排除）。
- 使用頻度が低いアセットを「アーカイブ済み」にし、実体だけをライブラリ外へ退避する機能。
- ストレージ上限、容量不足が予想される場合の通知。
- S3互換ストレージ／WebDAVをアセット保存先として直接使う機能。ローカルキャッシュ、再開可能な転送、認証情報のOS資格情報ストア保存が必要になるため、マウントドライブ対応とは別フェーズで扱う。

### 4.3 ストレージバックエンドの方針

- 初期版は `LocalDirectory` のみを実装する。これはユーザーが指定したローカルフォルダへのファイル操作であり、別ドライブも含む。
- DBには絶対パスを保存せず、「ストレージバックエンドの設定」と「そのルートからの相対オブジェクトキー」を分けて保存する。
- 将来の `S3` と `WebDav` は、同じオブジェクトキーで `put`、`get`、`exists`、`delete` を提供するバックエンドとして追加する。直接リモートへ置く場合も、一覧を軽く保つためサムネイルキャッシュはローカルに維持する。
- S3/WebDAVの認証情報はDBや設定ファイルに保存せず、OSの資格情報ストアへ保存する。

## 5. バックアップ

### 5.1 バックアップ先の設定

- ユーザーは設定画面でバックアップ先フォルダを指定できる。
- pCloud を使う場合は、可能ならローカル実体を持つ pCloud Sync フォルダを選ぶことを案内する。pCloud Drive の仮想マウント先もバックアップ先としては選べるが、回線断や遅延で失敗し得る旨を表示する。
- アプリは pCloud のアカウントや認証情報を扱わない。OS 上でユーザーがマウント・同期済みのフォルダへ通常のファイルコピーを行うだけとする。
- バックアップ先が利用不可の場合、ライブライブラリを変更・削除せず、失敗を記録して次の予定または手動実行で再試行する。

### 5.2 実行契機

- ユーザーが「今すぐバックアップ」を実行できる。
- 自動バックアップは既定で有効にし、ライブラリに変更があった場合に**一日一回まで**、アプリがアイドル中または正常終了時に実行する。
- 容量の大きい初回バックアップと、バックアップ先が仮想ドライブの場合は、開始前に対象容量を表示して確認を求める。
- インポート、移動、DB マイグレーションの途中には開始しない。実行中のライブラリ変更はキューに入れ、次回バックアップへ回す。

### 5.3 作成方法

1. SQLite のバックアップ API 等で、ローカルのTempサブフォルダに整合性の取れた DB スナップショットを作る。ライブの `library.db` を単純コピーしない。
2. 登録済みの管理ファイルをサイズ等で照合し、バックアップ先に存在しないものだけをコピーする。厳密なハッシュ照合は将来の任意機能とする。
3. DB スナップショット、対象ファイル一覧、ハッシュ、アプリ／スキーマ版、作成日時を含むマニフェストを作る。
4. すべてのコピーと検証が成功した後にのみ、バックアップを `complete` と記録する。
5. 途中で失敗したバックアップには `partial` 状態を残す。復元候補には出さず、後で再開または掃除できる。

ライブDBや `-wal`／`-shm` ファイルをクラウド先へそのまま同期しないことを必須とする。

`database-backups/` はライブDBがローカルで失われたときの復旧用であり、アセット保存先と同じ物理ドライブの故障・削除には備えられない。実際の災害復旧用には、後述の別バックアップ先へコピーする。

### 5.4 保存形式と世代管理

```text
<backup-destination>/VRAssetLibraryBackups/<library-id>/
├── objects/                            # ハッシュ単位のアセットコピー。一度だけ保存
├── snapshots/
│   ├── 2026-11-06T10-30-00Z/
│   │   ├── library.db
│   │   ├── manifest.json
│   │   └── COMPLETE
│   └── ...
└── latest.json
```

- `objects/` は不変として扱う。同じハッシュのアセットは、バックアップ先へ再コピーしない。
- スナップショットの `manifest.json` が、復元対象のアセットファイルと対応する object を列挙する。
- 既定の保持数は「日次7世代、週次4世代、月次12世代」とする。保存先の空き容量不足時は、自動削除せず利用者に通知する。
- 世代削除は必ずスナップショット単位とし、どの世代からも参照されない object だけを削除候補にする。削除前に対象容量を表示し、明示確認を求める。

## 6. 復元

- 設定画面からバックアップ先を選び、`COMPLETE` とマニフェスト検証に成功したスナップショットだけを一覧表示する。
- 復元は現在のライブライブラリを上書きしない。アプリローカルデータ領域へDBを復元し、アセット保存先は復元対象のストレージルートを選択して再接続する。
- DB、マニフェスト、全アセット object のハッシュ検証に失敗した場合、復元を完了扱いにしない。
- 外部参照のアセットは DB に情報だけ復元され、実体は再リンクが必要であることを表示する。

## 7. 完了条件

1. ローカルライブラリでDB、検索、タグ編集、サムネイル閲覧を行う際、pCloud の接続有無で失敗しない。
2. pCloud Sync フォルダをバックアップ先に選び、変更後のバックアップを作成できる。
3. バックアップ中に回線が切れても、ライブDBとライブアセットが壊れず、部分バックアップは復元候補に表示されない。
4. 同一アセットを含む複数世代のバックアップで、アセット実体がバックアップ先に重複保存されない。
5. 任意の完全スナップショットを新しいローカルフォルダへ復元し、アプリで開いて検索・ファイル参照できる。
