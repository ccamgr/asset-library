# ローカル VR アセットライブラリ — デスクトップ実装候補

まだ特定の技術へ確定しないための比較資料。前提は Windows を最優先としつつ、将来 macOS/Linux も選べる、ローカルファイル・SQLite・サムネイル一覧・ブラウザを開く機能を持つアプリである。

## 比較するときの軸

- **UI の作りやすさ**: サムネイルグリッド、検索、タグ、ドラッグ＆ドロップを気持ちよく作れるか。
- **ローカル操作**: 任意フォルダ、SQLite、ファイルコピー、画像縮小、OS のファイルマネージャ／ブラウザ起動を安全に扱えるか。
- **配布**: Windows インストーラー、コード署名、アップデート、依存ランタイムの扱い。
- **性能**: 数千件の一覧と、多数の大きな ZIP を読み込んでも操作感を保てるか。
- **将来性**: BOOTH 以外の取得元、圧縮ファイル解析、プラグイン的な取り込み先追加への拡張性。
- **開発体験**: チームが慣れている言語、UI を試作する速度、長期メンテナンスの容易さ。

## 候補一覧

| 構成 | 主な言語 | 向く場合 | 今回の相性 | 注意点 |
| --- | --- | --- | --- | --- |
| **Tauri 2 + React/Svelte/Vue + Rust** | TypeScript + Rust | Web UI の表現力と小さめの配布物を両立したい | とても高い | Rust と Web UI の二言語になる。OS WebView の差分は確認が必要 |
| **Wails + React/Svelte/Vue + Go** | TypeScript + Go | Go でファイル処理・DB・取り込みロジックを書きたい | 高い | Web UI なので Go だけで完結はしない。Tauri より採用判断はチームの Go 習熟度に依存 |
| **Flutter** | Dart | ネイティブ寄りで一貫した見た目、将来のモバイル展開も視野に入れる | 中〜高 | Web 技術に頼らず UI を完結できる。複雑なデスクトップ操作や OS 固有機能は事前検証が必要 |
| **Avalonia UI** | C#/.NET | C# に慣れており、Windows を重視しつつクロスプラットフォームも欲しい | 高い | .NET 前提。Windows 専用に絞れるなら WPF/WinUI も有力 |
| **WPF / WinUI 3** | C#/.NET | 対象を Windows 専用と割り切り、Windows らしいアプリにしたい | 高い（Windows 専用） | macOS/Linux 対応を後から足すのは難しい |
| **Qt / PySide / Qt for Python** | C++ / Python | リッチなネイティブ GUI、画像・ファイル操作を厚く扱いたい | 中〜高 | UI は強力。配布、ライセンス、Python 同梱サイズを計画する必要がある |
| **Fyne + Go** | Go | Go だけで比較的シンプルなデスクトップアプリを早く作りたい | 中 | カスタム性や洗練された大量サムネイル UI は、Web UI より手間が掛かりやすい |
| **egui / Slint / Iced + Rust** | Rust | Rust に統一し、独自 UI・軽量さを重視したい | 中 | 本件のような情報整理 UI では成熟した Web UI より実装量・検証量が増えやすい |

## 大きく分けると

```text
Web UI を使う
├── Tauri + Rust       : 軽量、権限を細かく絞りやすい
├── Wails + Go         : Go のローカル処理と組み合わせやすい

ネイティブ UI を使う
├── Avalonia / WPF / WinUI : C#、Windows を重視するなら強い
├── Flutter                : Dart、見た目をプラットフォーム間で揃えやすい
├── Qt                     : C++/Python、デスクトップ GUI の伝統的な選択肢
├── Fyne                   : Go 一本で作る選択肢
└── egui / Slint / Iced    : Rust 一本で作る選択肢
```

## Go を選ぶ場合の具体案

### Wails + TypeScript UI + Go

Go はアプリの「裏側」に置く。SQLite、ファイルコピー、ハッシュ計算、ZIP 読み取り、サムネイル生成、BOOTH 情報の取得を Go が担当し、React/Svelte などがライブラリ画面を担当する。

```text
React/Svelte UI ── 呼び出し ── Go のアプリ層 ── SQLite / ファイル / ネットワーク
```

「Go を主力にしたい」場合の最有力。HTML/CSS でサムネイルグリッド・タグ選択・検索 UI を作れるので、純ネイティブ GUI より見た目を素早く詰めやすい。

### Fyne + Go

Go だけで画面からロジックまで書く案。小さなユーティリティには魅力的だが、今回のように一覧・詳細・検索・フィルター・DnD が中心のアプリは、UI の作り込み量を見積もってから選ぶのがよい。

## Rust を選ぶ場合の具体案

### Tauri 2 + TypeScript UI + Rust

Rust はファイルや DB を扱うコア層、React/Svelte/Vue は画面層にする。アプリからアクセスできるファイル操作や外部 URL 起動を許可リストで制限する設計にしやすい。SQLite の公式プラグインとマイグレーションの仕組みもある。[Tauri の概要](https://v2.tauri.app/start/) [SQL プラグイン](https://v2.tauri.app/plugin/sql/)

```text
React/Svelte UI ── invoke ── Rust のアプリ層 ── SQLite / ファイル / ネットワーク
```

今回の「外部から入手したファイルを扱う」性質に合う。UI は Web、危険になりやすい操作（任意パス読み書き、外部 URL、アーカイブ解析）は Rust 側へ閉じ、UI には必要なコマンドだけ公開する。

### egui / Slint / Iced + Rust

Rust 一言語に統一できる。ただしこの種の資産管理 UI では、テーブル、複雑なフィルター、コンテキストメニュー、アクセシビリティなどを Web UI と同水準に揃えるコストを、最初に小さく試作して判断したい。

## 実装言語とは別に固定したい設計

どの候補でも、コアを UI から分離しておくと乗り換えやテストがしやすい。

```text
画面層
  └─ アプリケーション層（AssetService / ImportService / SearchService）
       ├─ SQLite リポジトリ
       ├─ ライブラリフォルダ操作
       ├─ サムネイル生成
       ├─ アーカイブ解析
       └─ 配布元メタデータ取得（BOOTH / Gumroad / 手動）
```

- DB は SQLite。DB に実ファイルを詰めず、アセット用フォルダと相対パスを保存する。
- ファイル操作はアプリケーション層に集約し、UI から任意パスを直接触らせない。
- BOOTH の取得は交換可能な `SourceAdapter` として実装し、失敗しても手動登録にフォールバックする。
- アセット間リンクは `AssetRelation` テーブルに保持し、配布元に依存しない。

## 迷ったときの試作順

最終決定前に、候補を二つに絞ってそれぞれ半日〜数日程度で次を作ると比較しやすい。

1. 任意のライブラリフォルダを設定する。
2. ZIP を複数ドロップし、SQLite に資産とファイルを登録する。
3. 1,000 件のダミー資産をサムネイル付きでスクロール・タグ検索する。
4. ファイルの格納先と商品 URL を開く。
5. ライブラリフォルダを丸ごと別パスへコピーして再オープンする。

この試作で、特に UI の組みやすさ、Windows 配布物の体積、ファイル選択／DnD、開発者が無理なく保守できるかを比べる。

## 現時点の主な候補（決定ではない）

| 候補 | 採用する決め手 | 先に確かめること |
| --- | --- | --- |
| **Tauri 2 + React/Svelte + Rust** | 一覧・タグ・検索の UI を早く高品質に作り、Rust でローカル処理を堅くしたい | OS WebView 上での大量サムネイルと DnD の操作感 |
| **egui + Rust** | Rust 一本で、軽量でネイティブなツールとして作り切りたい | 大量一覧、複雑なフィルター、アクセシビリティ、OS 標準に近い操作の実装コスト |
| **Wails + React/Svelte + Go** | ファイル処理・圧縮ファイル解析・将来のツール連携を Go で素直に書きたい | Go と Web UI の境界、Windows WebView 上の UI 品質 |
| **Fyne + Go** | Go 一本で早く小さな実用ツールを出したい | サムネイル中心のリッチな管理画面をどこまで気持ちよく作れるか |

Electron は Chromium 同梱によるサイズ・メモリ使用量のトレードオフが、このアプリには見合わないため候補外とする。

「Rust が良いから Tauri」「Go が良いから Wails」と先に決めるより、作る人が継続して触れる言語と、最初に必要な UI の品質で選ぶのがよい。どれも SQLite とローカルフォルダ構成は問題なく実現できる。
