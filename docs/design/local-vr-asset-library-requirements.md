# ローカル VR アセットライブラリ — 要件・設計たたき台

## 1. 目的

BOOTH、Gumroad などから入手した VRChat 用アセットを、**ダウンロード元に依存せずローカルだけで検索・整理・保全できるデスクトップアプリ**として管理する。

公式の購入履歴・ダウンロード機能を置き換えるのではなく、すでに保持している ZIP、UnityPackage、フォルダや、複数ストアで取得したデータを一つのライブラリとして扱う。ネットワークに接続しなくても、メタデータ、サムネイル、検索、タグ、カテゴリ、ファイル閲覧が利用できることを基本とする。

## 2. 想定利用者と代表的な利用場面

個人の VRChat ユーザー／アバター改変者が、数十〜数千の購入・無料配布アセットを所有しているケースを想定する。

1. 以前 BOOTH からダウンロードした ZIP 群をアプリの保管場所へ入れ、一覧化する。
2. 「衣装」「桔梗対応」「無料」「改変済み」などで絞り込み、必要なアセットの保存先を開く。
3. 商品ページやショップページを開き、更新版・利用規約・対応アバターを確認する。
4. Gumroad、GitHub 配布、Discord 配布、自作物なども、同じ操作で手動登録する。
5. アプリ用フォルダだけをバックアップ／別 PC にコピーして、そのまま復元する。

## 3. MVP（最初に提供する範囲）

### ライブラリと保存先

- 初回起動時に「ライブラリフォルダ」を選択できる。既定値は OS のアプリデータ領域配下（例: Windows では `%LOCALAPPDATA%/VRAssetLibrary`）とする。
- ライブラリフォルダ内にデータベース、サムネイル、インポート済みアセットを置く。
- 別ドライブ、NAS 同期フォルダ、クラウド同期対象フォルダなど、任意のパスを指定できる。
- アプリがファイルをコピーして管理する方式を既定にし、元データを残したまま参照だけする「外部参照」も選べる。
- データの削除は OS のごみ箱を優先し、DB からのみ消す操作と、実ファイルも消す操作を明確に分ける。

### 登録・インポート

- ファイルまたはフォルダをドラッグ＆ドロップして登録できる。
- ZIP、7z、RAR、UnityPackage、各種圧縮ファイル、フォルダを扱える（内容の展開は後続機能でもよい）。
- **一つのアセットに複数の配布ファイルを紐付けられる。** 例: 本体 ZIP、追加テクスチャ、更新版、導入説明 PDF、購入時に分割されていた複数 ZIP。詳細画面では各ファイルを個別に開く／格納場所を開く／外すことができる。
- 複数ファイルをまとめて新規アセットへ登録するほか、既存アセットへ後からファイルを追加できる。同一商品の旧版・新版を残すか、旧版を置換扱いにするかを選べる。
- 登録時に名前、配布元、商品 URL、ショップ URL、作者名、バージョン、入手日、価格／無料、メモを編集できる。
- 複数ファイルを一括登録でき、共通タグ・カテゴリをまとめて付与できる。
- 同じファイル名・ハッシュ・商品 URL が存在する場合、重複候補として提示する。

### BOOTH 対応

- BOOTH 商品 URL を貼ると、商品 ID を記録し、公開ページから取得可能な範囲で商品名、ショップ名、サムネイル、説明、タグ、公開 URL を下書きに反映する。
- 取得に失敗しても URL と手入力情報だけで登録を完了できる。
- 購入状態やダウンロード権限に依存する情報を無理に収集しない。ログイン情報、Cookie、パスワードは保存しない。
- 商品ページ／ショップページを OS 標準ブラウザで開ける。
- 後から「商品情報を再取得」できる。取得日時と、取得内容を手編集した項目を区別して、再取得で手編集内容を勝手に上書きしない。

### 整理・閲覧

- グリッド／リスト表示、サムネイル表示、名前・作者・入手日・更新日でソート。
- 任意個のタグ（例: `衣装`、`アクセサリー`、`シェーダー`、`桔梗`、`無料`）を付与、タグで AND／OR 絞り込み。
- 階層カテゴリ（例: `アバター > 対応衣装`、`ワールド > ギミック`）を割り当てる。カテゴリは原則一つ、必要なら将来複数対応にする。
- 名前、作者、ショップ、タグ、メモ、ファイル名を横断検索する。
- 詳細画面でサムネイル、配布元リンク、関連ファイル、タグ、カテゴリ、メモ、変更履歴を確認できる。
- ファイルまたは格納フォルダをエクスプローラーで開ける。
- アセット同士を関連付けられる。関連先のアセット詳細へ移動でき、ライブラリ内に未登録の関連商品は URL とメモだけを仮登録できる。

### サムネイル

- BOOTH から得られた商品画像、またはユーザーが指定したローカル画像をアセットの代表サムネイルとして保存する。
- 画像がない場合はプレースホルダーを表示する。
- サムネイルはライブラリ内へコピーして保存し、元 URL が失効・変更されても一覧が壊れないようにする。

### バックアップと可搬性

- ライブラリフォルダを丸ごとコピーすれば復元できる。DB は相対パスを基本とし、ライブラリ配下のファイルを別 PC でも検出できる。
- 外部参照のアセットは、バックアップ対象外であることを UI 上に明示する。
- 「バックアップ対象の容量」「外部参照の件数」「リンク切れ」を確認する画面を用意する。
- DB を JSON/CSV にエクスポートできると、アプリの将来的な移行にも強い。

## 4. 保存レイアウト案

```text
VRAssetLibrary/                       # ユーザーがバックアップする単位
├── library.db                        # SQLite データベース
├── assets/
│   ├── 01H.../                       # アセットごとの安定した UUID
│   │   ├── files/                    # インポート方式なら実体をここへ配置
│   │   │   └── KIKYO_Clothes_v1.2.zip
│   │   └── cover.png                 # 任意: このアセットのカバー画像
│   └── ...
├── thumbnails/                       # 生成済み縮小画像キャッシュ
├── exports/                          # 任意: メタデータ書き出し先
└── backups/                          # 任意: DB 自動バックアップ
```

`library.db` は SQLite を想定する。単一ファイルでトランザクション、検索、移植性を満たし、ローカル専用アプリに適する。アセット実体を DB に BLOB として入れず、通常ファイルとして保持することで、復旧・手作業確認・差分バックアップをしやすくする。

ライブデータはローカルディスクに置き、pCloud 等のクラウドマウントはバックアップ先としてのみ使う。容量管理、バックアップ作成、世代管理、復元手順の詳細は [ローカル保存・容量管理・バックアップ要件](local-storage-and-backup-requirements.md) を参照。

## 5. 最小データモデル

| エンティティ | 主な項目 | 補足 |
| --- | --- | --- |
| Asset | id, title, creator, source, product_url, shop_url, description, acquired_at, version, price, note, cover_path | ライブラリ上の一件 |
| AssetFile | id, asset_id, storage_mode, relative_path / external_path, filename, size, hash, added_at | 一件に複数ファイルを紐付ける |
| Tag | id, name, color | 重複しないタグ辞書 |
| AssetTag | asset_id, tag_id | 多対多 |
| Category | id, parent_id, name, sort_order | 階層カテゴリ |
| AssetCategory | asset_id, category_id | MVP では Asset 側の category_id でもよい |
| SourceMetadata | asset_id, source_type, remote_id, fetched_at, raw_json | BOOTH 等から取得した情報と再取得の基盤 |
| AssetRelation | source_asset_id, target_asset_id, relation_type, note, created_at | アセット間の有向リンク。重複を防ぐ |
| Activity | id, asset_id, type, occurred_at, details | 登録・更新・再取得などの履歴 |

`storage_mode` は `managed`（ライブラリ配下へコピー／移動）と `external`（元の絶対パスを参照）を持つ。`hash` は SHA-256 などで保存し、改名後の重複判定と整合性チェックに使う。

`AssetRelation.relation_type` は自由記述タグではなく、候補から選ぶ方式にすると検索と表示を揃えやすい。初期候補は次のとおり。

| 関係 | 向きの例 | 用途 |
| --- | --- | --- |
| `addon_for`（追加・拡張） | 追加ギミック → 衣装本体 | ギミック、追加機能、差分 |
| `compatible_with`（対応） | 衣装 → アバター | 対応アバター・対応システム |
| `requires`（必須） | 拡張物 → 前提アセット | 導入に必要な本体・シェーダー |
| `variant_of`（派生） | 改変版 → 元アセット | カラバリ、改変版、移植版 |
| `related_to`（関連） | 双方向扱い | セット品、作者推奨、用途が近いもの |

たとえば「衣装 A」と「別ショップの衣装 A 用揺れ物ギミック B」は、B から A へ `addon_for`、または B から A へ `requires` を張る。詳細画面では A 側に「追加・拡張」、B 側に「必要なアセット」として逆向きも自動表示する。これにより、片方だけを見つけたときにも依存関係をたどれる。

## 6. 画面構成案

1. **ライブラリ** — 検索、絞り込み、並び替え、グリッド／リスト、追加ボタン。
2. **アセット詳細** — カバー、メタ情報、タグ・カテゴリ編集、複数ファイルの一覧、関連アセット、リンクを開く、履歴。
3. **追加／編集ダイアログ** — ファイル選択、保存方式、URL からの BOOTH 情報取得、手入力、重複確認。
4. **タグ・カテゴリ管理** — 改名、統合、階層変更、未分類の確認。
5. **ライブラリ設定** — ライブラリフォルダの変更、バックアップ対象、DB の書き出し、リンク切れ検査。

## 7. BOOTH 連携の境界と注意点

- MVP は「公開商品ページの補助的なメタデータ取り込み」に限定する。購入履歴の同期や自動ダウンロードは扱わない。
- 公開ページの HTML 構造は変わり得るため、URL だけで登録を完遂できる設計にする。取得結果は補助情報であり、失敗を登録不能の理由にしない。
- 自動取得の頻度を抑え、ユーザーが明示的に実行したときにのみ更新する。利用規約・robots.txt・提供 API の有無を実装前に確認する。
- URL 正規化（クエリ除去、末尾スラッシュ統一）と商品 ID の保存で、同一商品の重複を減らす。

## 8. 後続フェーズで価値が高い機能

- 圧縮ファイル内の `README`、`package.json`、UnityPackage 情報を解析し、名前・対応アバター・バージョン候補を提案。
- `.unitypackage` の内容一覧、ZIP 内のプレビュー、テキスト検索。
- 「アバター対応」「利用規約」「導入済み／未導入」「お気に入り」「更新確認待ち」などのスマートコレクション。
- ファイルハッシュによる重複統合、壊れた外部参照の再リンク支援。
- BOOTH 以外のコネクタ（Gumroad、itch.io、GitHub Releases、手動 URL）。どれも同じ `SourceMetadata` インターフェースで追加できる構造にする。
- 変更監視、増分バックアップ、暗号化バックアップ、NAS を含むライブラリ健全性チェック。
- アセットごとのライセンス文書・導入手順・自分用の改変メモを添付／検索。

## 9. MVP で意図的にやらないこと

- BOOTH/Gumroad のアカウントログイン、購入履歴の完全同期、自動ダウンロード。
- 複数端末のリアルタイム同期・共同編集。
- Unity プロジェクトへの自動インポート／依存関係解決。
- 購入ライセンスの有効性判定や配布元の権利管理。

これらは認証・規約・セキュリティ・障害時の責務を大きく広げるため、まずは「手元にあるデータを安全に見つけられる」ことを完成させてから検討する。

## 10. 決めると実装方針が固まる質問

1. 対象 OS はまず Windows 専用にするか、macOS/Linux も最初から対象にするか。
2. 保管方式は「常にアプリ管理フォルダへコピー」を既定にしてよいか。元ファイルを動かしたくない利用者向けに外部参照も初期版で必要か。
3. BOOTH の情報取得は URL 貼り付け時の明示実行だけでよいか、それともブラウザから URL を取り込む導線が必要か。
4. アセットの主な単位は「ダウンロードファイル一つ」か、「同じ商品の複数バージョン／追加ファイルを束ねた商品一つ」か。
5. 将来的に、端末間同期やスマホからの閲覧まで求めるか。

## 11. 推奨する初期リリース判定

次の一連の作業を、ネットワークなしでも完結できれば初期リリースとして実用的である。

> ZIP をドラッグ＆ドロップ → 名前・タグ・カテゴリを付ける → 一覧のサムネイルから見つける → 商品ページまたは格納フォルダを開く → ライブラリフォルダ全体をバックアップして別 PC で復元する。

その後に BOOTH URL の情報補完を追加すると、ローカル完結という核を壊さず、入力の手間を大きく下げられる。
